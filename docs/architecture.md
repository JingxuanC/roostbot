# 架构

## 一张图

```
浏览器 / 手机 / 桌面瘦客户端
        │  配对会话（无密码，见 §认证）
        ▼
┌──────────────────────────────────────────────┐
│ 控制面 control plane（apps/api，自研）         │
│ 账号 · 租户 · 工作区 · 成员/角色               │
│ 调度（起停容器）· 反代 · 配额 · 审计           │
└───────┬───────────────────────────┬──────────┘
        │ runtime token + 反代       │ 配对通道
        ▼                           ▼
┌──────────────────────┐   ┌──────────────────────┐
│ 云上 workspace 容器   │   │ 用户本机的 DSH        │
│  dsh --profile <ws>  │   │  （apps/local-agent） │
│  ├ Bot 团队           │◄──┤  只出站连接，不开端口  │
│  ├ 插件族（可选）      │   │  本机工具 / 文件      │

└──────────┬───────────┘
           │ 只读
           ▼
```

## 三个层次

### 1) 控制面

自研，TypeScript + Fastify（与 DSH 同栈，反代用 undici）。职责：

- 账号与配对（§认证）
- 租户 / 工作区 / 成员 / 角色（RBAC）
- 容器生命周期：创建、启动、健康、drain、停止、快照
- 反代：浏览器只与控制面通信，控制面用短时 runtime token 访问容器
- 配额与计量：容器秒、回合数、工具调用数、存储
- 审计：谁在什么时候让哪个 Bot 做了什么

控制面**不**碰模型调用，也**不**存 Bot 的业务数据。

### 2) 云上运行时（一个 workspace 一个 DSH）

- 容器里跑 `dsh --profile <ws> --base-path /w/<id>`
- profile 在镜像里预置：基线插件 + 该租户授权的插件
- 状态：`$DSH_HOME` 挂卷；会话、Bot 状态、记忆索引都在卷里
- 沙箱：回合级（见 §沙箱）

### 3) 本地 DSH（配对节点）

- 用户在电脑上装 `roostbot local`（一个 DSH 插件 + 一个守护进程）
- **只出站**：连控制面的 WebSocket，不需要公网 IP、不开放端口
- 能力：本机文件、本机 MCP、本机模型额度、本机 bash
- 云上 Bot 需要"够得着"时，控制面把调用路由到这条出站通道

## 认证

**配对为主，OIDC 为辅**（参考 OpenMausBot 的实践）：

1. 控制面生成一次性配对码（短时、单次）
2. 客户端（浏览器/桌面/本地节点）用配对码换长期会话
3. 会话 30 天，剩一半以上使用时续期，配对后最长 180 天
4. 企业客户可接 OIDC（Google / 飞书 / 自建）

三种 token 严格分开（见 `docs/decisions/0003-tokens.md`）：

| token | 谁持有 | 用途 |
|---|---|---|
| 会话 token | 客户端 | 访问控制面 |
| runtime token | 控制面 → 容器 | 访问该 workspace 的 DSH |
| provider token | 用户 → 密钥服务 → 模型代理 | 调模型/数据源（BYO） |

## 沙箱（回合级）

DSH 插件在同进程运行，这是 DSH 的能力，也是它的风险。补偿手段：

- **一个回合一个盒子**（bubblewrap / gVisor）：engine、shell、MCP 在盒内
- 盒内可见：只读镜像、`HOME`、本回合工作目录、该 Bot 的文件夹
- 盒内不可见：其他 Bot 的文件夹、`$DSH_HOME` 的会话与密钥、其他回合的进程
- 网络：默认无出网；需要出网时经控制面白名单代理
- 环境变量白名单

## 租户模型（三层）

| 层 | 形态 | 隔离手段 | 适用 |
|---|---|---|---|
| **T0 个人云** | 一人一个容器 | 容器边界 | 默认 |
| **T1 团队云** | 一台机器多人共用 | audience 规则（数据面）+ 回合沙箱（进程面） | 可信小团队 |
| **T2 强隔离** | 一租户一容器/一机 | 容器 + 网络 | 企业、不可信租户 |

T1 是成本关键：让一台机器的成本被多人分摊，同时不牺牲数据隔离——隔离靠规则和沙箱，不是靠容器。

## 数据与事件

- **事件是事实源**：`user.message` / `bot.message` / `tool.call` / `approval.request` / `run.settled`
- 房间事件存工作区卷里的 SQLite（每房间 append-only），控制面只保留索引
- 计量、审计、多端一致性都从事件派生
- 记忆（causal-memory）从事件里抽取"判断"，不存聊天全文

## 与 DSH 的关系

- DSH 是运行时内核，**不改内核**
- 我们提供：插件（Bot 团队、面板）、控制面、沙箱、配对节点
- 需要 DSH 补的能力列在 `docs/runtime-contract.md`（七条）

## 部署形态

| 阶段 | 形态 |
|---|---|
| v0 | 一台 VPS：控制面 + 一个 workspace 容器 + 反代（Caddy） |
| v1 | 控制面独立部署；容器按用户创建；本地节点配对可用 |
| v2 | 多区域、卷快照迁移、计费、企业 SSO |
