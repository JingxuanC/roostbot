# SLO：可用性、延迟与错误预算

> 状态：建议（M6-6.8 / D3）。指标来自控制面 `/metrics` 与 `/healthz`；
> 没有实现多实例、长期存储或告警后端，本文只定义口径与阈值。
>
> 适用对象：单机控制面（`apps/api`）。沙箱、DSH Web、模型 provider 的 SLO 不在本文范围。

## 1. 服务边界

| 纳入 SLO | 不纳入 SLO |
|---|---|
| 控制面 HTTP API（配对、房间、消息、Bot、审批、用量等） | 模型推理质量与延迟（BYO provider） |
| SSE 连接建立与增量投递 | DSH Web 插件面板（第三方界面） |
| 租约/调度 tick 的可用性（间接） | 沙箱内工具执行（OpenShell 依赖） |
| `/healthz` 探活 | 静态页面的像素级正确性 |

## 2. SLI 与 SLO（建议值）

### 2.1 可用性

**SLI**：外部探针每 30s 请求 `GET /healthz`，200 且 JSON `ok=true` 记为成功。

**SLO**：滚动 30 天可用性 **99.9%**。

**错误预算**：30 天约 43m 12s 不可用（`30 × 24 × 60 × 0.001`）。

注意：`/healthz` 只返回进程内状态，**不查询 SQLite**。数据库损坏/磁盘满时它仍可能 200。
因此可用性 SLI 还要叠加“5xx 比例”作为第二证据（见 §2.2）。

### 2.2 HTTP 错误率

**SLI**：非 SSE、非 `/metrics` 的请求中，5xx 占比。

```
sum(rate(roost_http_requests_total{status=~"5..",path!~"/api/rooms/:id/stream|/w/:workspaceId/dsh/.*|/metrics"}[5m]))
/
sum(rate(roost_http_requests_total{path!~"/api/rooms/:id/stream|/w/:workspaceId/dsh/.*|/metrics"}[5m]))
```

**SLO**：5xx 比例 30 天 ≤ 0.1%（与 99.9% 可用性对齐）。

- 4xx 是客户端错误，不计入可用性；但 401/403 突增要单独排查（配对/Origin/权限变更）。
- 429 不计入可用性，按容量/滥用单独看。
- `/w/.../dsh/*` 的 502 单独统计（上游 DSH 不可用，不等于控制面不可用）。

### 2.3 延迟

**SLI**：控制面 HTTP 请求耗时直方图（buckets 0.01/0.05/0.1/0.5/1/5s）。

```
histogram_quantile(0.95,
  sum by (le) (rate(roost_http_request_duration_seconds_bucket{path!~"/api/rooms/:id/stream|/w/:workspaceId/dsh/.*|/metrics"}[5m]))
)
```

**SLO**（建议）：

| 指标 | 目标 |
|---|---|
| p95 | < 500ms |
| p99 | < 2s |

SSE 是长连接，耗时没有意义；不要把它算进延迟。SSE 的可用性用“连接建立成功 + 15s 心跳”观察。

### 2.4 业务队列（辅助 SLI）

| 指标 | 含义 | 建议目标 |
|---|---|---|
| `roost_runs_queued` | 排队中的调度 run | 通常 < 5；持续 > 20 视为异常 |
| `roost_pending_approvals` | 待审批数量 | 无硬目标；持续上升说明审批积压 |
| `roost_plugins_installing` | 等待沙箱 sync 的安装 | 通常 < 3；持续 > 0 超过 30 分钟视为卡住 |

这三个 gauge 在每次抓取时从 SQLite 现查；`memory` 模式恒为 0。

## 3. 告警建议

### 3.1 分页（P1）

| 告警 | 条件 | 说明 |
|---|---|---|
| 控制面不可用 | 外部探针 `/healthz` 连续 3 次失败（约 90s） | 进程崩溃/端口不通/反代故障 |
| 5xx 突增 | 5xx 比例 > 1% 持续 5 分钟 | 数据库/代码/磁盘 |
| 延迟严重劣化 | p95 > 1s 持续 10 分钟，或 p99 > 5s 持续 5 分钟 | 先看 SQLite 与磁盘 |
| DSH 反代不可用 | `/w/:workspaceId/dsh/.*` 的 502 比例 > 50% 持续 10 分钟 | 插件面板不可用；核心聊天不受影响 |

### 3.2 工单（P2）

| 告警 | 条件 |
|---|---|
| 5xx 缓慢升高 | 5xx 比例 > 0.1% 持续 30 分钟 |
| p95 超目标 | p95 > 500ms 持续 15 分钟 |
| 调度积压 | `roost_runs_queued > 20` 持续 10 分钟 |
| 审批积压 | `roost_pending_approvals > 20` 持续 1 小时（按团队规模调整） |
| 插件安装卡住 | `roost_plugins_installing > 0` 持续 30 分钟 |
| 限流异常 | 429 比例 > 1% 持续 10 分钟（先按账号排查，不直接调阈值） |
| 磁盘 | 数据盘使用率 > 80%（需要 node_exporter 或云监控；控制面没有磁盘指标） |
| WAL 膨胀 | `roost.db-wal` 持续 > 1GB（外部脚本；控制面没有该指标） |

### 3.3 错误预算策略（建议）

- 预算消耗 > 50% 且周期未过半：暂停高风险迁移/大面积改动，先修稳定性。
- 预算耗尽：只允许修复类变更；下一次发布前补做故障演练。
- 单次事故 > 10% 预算：必须写复盘，并在 `docs/design/observability.md` 补指标缺口。

## 4. 采集与口径注意事项

1. **指标是进程内内存计数**：控制面重启后计数器归零。Prometheus `rate()` 能处理计数器重置，
   但短窗口会出现尖刺；跨重启的月度统计应以外部探针与长期存储为准。
2. **只有单实例**：没有 `instance` 标签，也不需要 `sum by (instance)`；多实例部署本身不支持。
3. **path 标签已归一成路由模板**，未识别路径为 `other`；不要用原始 URL 做聚合。
4. **`/metrics` 无鉴权**，不要让公网直接抓；只允许监控网段或本机。
5. **没有的指标**：SQLite 查询耗时、磁盘、沙箱状态、调度 tick 成功/失败、SSE 首字节。
   这些只能从日志/外部探针补；属于已知缺口，不要用现有指标假装覆盖。
6. **审计与告警分开**：`GET /api/audit` 是查询接口，不是告警源；告警从 `/metrics` 与外部探针来。

## 5. 降级策略

| 故障 | 用户可见行为 | 平台动作 |
|---|---|---|
| SQLite 不可写/损坏 | 写接口 5xx；读可能部分失败 | 先停写、备份现场、从最近备份恢复；不要自动覆盖 |
| 磁盘满 | 上传 507/5xx；SQLite 写失败 | 清理附件 GC 或扩容；先保数据库 |
| 控制面重启 | 请求短暂失败；SSE 断开 | 客户端按 `after=seq` 重连补拉；限流桶重置 |
| 调度 tick 停止 | 定时任务不触发，手动接口仍可用 | 检查 `ROOST_SCHEDULER` 与日志；恢复后按 12h catch-up 补 |
| 沙箱不可用 | 房间回合失败/超时；已有消息仍可读 | 面板与沙箱功能降级；核心控制面继续服务 |
| DSH Web 不可用 | 插件面板 502/空白 | 隐藏面板入口；房间/Bot/设置不受影响 |
| 模型 provider 故障 | Bot 不回或报错 | 平台不代理推理；提示用户检查 BYO 凭据 |
| 反代缓冲导致 SSE 延迟 | 消息成批到达 | 修正 `proxy_buffering off`；客户端仍能按 seq 去重 |

**当前没有的能力**：读只读模式、自动故障转移、跨机热备、按 workspace 隔离降级。
这些不在 v0/M6 范围内，不要在对客承诺里写成已有能力。
