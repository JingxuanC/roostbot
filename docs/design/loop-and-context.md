# Loop 与上下文：Bot 的本质

> 状态：原则（2026-11-03）。本文是我们做所有 Bot 相关决定的**第一性原理**，其他设计文档都应能指回这里。

## 1. 三句话

1. **Bot 的本质是一个 loop**：读上下文 → 调模型 → 解析动作 → 执行 → 把结果写回上下文 → 再读。
2. **模型是无状态的**：它唯一的状态是这一轮进来的那段 token；上一轮发生过什么，完全取决于我们重新喂了什么。
3. **所以所有能力本质上都是上下文工程**：技能是打包好的上下文，MCP 是工具 schema 加上工具结果文本，“记忆”是把状态投影进上下文。

推论：**凡是“记住”“权限”“协作”“定时”这些问题，最终都要落成“往上下文里放什么、按什么顺序、用多少预算”。**

## 2. Loop 的形状

```
        ┌────────────────────────────────────────────┐
        │  context assembly                          │
        │  system · persona · skills · tool schemas  │
        │  · retrieved memory · conversation · files │
        └──────────────────┬─────────────────────────┘
                           ▼
                    model(tokens) ──► 动作或回答
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
        工具执行（副作用）           结束/等待/失败
              │
              ▼
        observation 写回上下文 ──────────► 下一轮
```

**Stop 条件必须是显式的**：预算（token/时间/工具次数）、无进展、需要人、任务完成。没有显式 stop 的 loop 就是烧钱机。

## 3. 无状态的三条硬推论

| 推论 | 后果 |
|---|---|
| 模型不记得上一轮 | 我们必须在外面存：会话日志、记忆、文件、状态机 |
| 同一轮里模型看不到“刚刚执行了什么”，除非我们写回去 | 每个工具调用都必须产出可注入的 observation |
| 进程崩溃后 loop 只能从我们保存的状态重来 | 副作用必须幂等（effect 队列），否则重试会重复发送/重复提交 |

这正是 OpenMausBot 那套 **assignment 状态机 + effect 队列**、superagent 那套 **pass/effect 队列 + 恢复**存在的原因：它们不是“架构洁癖”，是给无状态模型补状态。

## 4. 上下文里有什么（以及各自的成本）

| 段 | 内容 | 谁决定 | 预算策略 |
|---|---|---|---|
| system / persona | 人设、规则、合规边界 | 人写，单一 builder 组装 | 固定，稳定段可缓存 |
| skills | 技能正文 + 示例 | 装配时按名字取 | 索引常驻、正文按需（OMB 的索引段+正文段） |
| tool schemas | 每个工具的 JSON schema | 由能力清单决定 | **schema 本身就是成本**：superagent 的工具桥把它从 43–57KB 压到 14.5KB（−65~74%） |
| memory | causal-memory 检索结果 | 回合开始注入 | 严格上限，按 audience 过滤 |
| conversation | 最近消息 | 日志投影 | 只取最近 N 条（OMB 默认 30）+ 摘要段 |
| tool results | 观察 | 工具返回 | **只注入摘要 + 引用**，长内容落文件 |
| files / workspace | 工作目录 | 模型自己读 | 按需读取，不预注入 |

**关键认识**：这一张表就是产品成本的来源。任何新功能，如果它不能回答“它给上下文加了多少 token、什么时候加”，就不该上。

## 5. 于是每个概念都要重新定义

| 我们常说的 | 真实机制 | 设计含义 |
|---|---|---|
| Bot | loop + 上下文配方（persona/skills/tools）+ 外部状态 | 换模型不该改变 Bot 身份；人设是数据不是代码 |
| Skill | 打包的上下文（正文 + 可选脚本） | 要版本化、要能按需取、要能计量它占的 token |
| MCP / Tool | 一张 schema（进上下文）+ 一次调用（出上下文）+ 一段文本（回上下文） | 工具越多，schema 越贵；要“未授权即不可见”，而不是“授权了再拒绝” |
| Memory | 把外部状态投影进上下文的一次检索 | 记忆的价值 = 它替代了多少上下文；不是越多越好 |
| Permission | 进上下文之前的**过滤器** + 执行时的门 | 未列出的工具对模型不可见（deny-invisible），比事后拒绝省 token 也更安全 |
| Approval | loop 中途的一次人工注入 | 是上下文事件，要带“为什么被拦” |
| Schedule | 由一个外部时钟**启动** loop | 定时器不在模型里，模型只负责被叫醒之后的事 |
| Workspace | loop 之外的持久基质 | 卷赢了，loop 才可以随便重启 |
| Team / 群聊 | 多个 loop 共享一份事件日志，各自投影 | 每个成员的上下文是“同一日志的不同投影”，不是共享内存 |

## 6. 由这条原理推出的七条工程规则

1. **上下文单一装配点**：只有一个 builder 决定顺序与预算（OMB 的 `system-prompt.ts` 就是这么做的）。多处拼 prompt 一定漂移。
2. **稳定段与易变段分开**：稳定段在前（可缓存），易变段在后。直接省钱，也让对比调试可行。
3. **每轮产出 Context Manifest**：注入了哪些段、各多少 token、哪些被丢弃、为什么。没有 manifest 就无法回答“为什么这次贵”。
4. **长观察必须外置**：工具输出超过阈值就写文件，上下文只留摘要 + 路径 + 后续读取方法。
5. **压缩是一等公民**：接近窗口阈值就压缩或换 part（OMB 0.9 压缩、0.8 预判），不能让模型自己扛。
6. **副作用幂等**：loop 会崩、会重试，所有对外动作走 effect 队列，键唯一。
7. **投影而非共享**：多人/多 Bot 场景下，各自从事件日志投影自己的上下文；共享内存会导致权限与成本同时失控。

## 7. 反模式（我们踩过或差点踩的）

| 反模式 | 后果 |
|---|---|
| 把历史全量塞上下文 | 成本线性上涨，且模型注意力被稀释 |
| 用“模型记得”当状态 | 换会话/重启即丢；多端看到不同事实 |
| 工具越多越好 | schema 撑爆窗口，模型选择变差 |
| 记忆当成无限知识库 | 检索质量下降，token 上涨，结论互相矛盾 |
| 每个功能各自拼 prompt | 顺序与预算不可控，缓存失效 |
| 定时任务直接往房间发用户消息 | 触发其他 Bot，成本与噪声扩散 |

## 8. 可测量的指标（每个 workspace 都要有）

| 指标 | 为什么要 |
|---|---|
| 每轮 input tokens 的分段构成 | 找出哪一段在涨 |
| cache hit rate（稳定段命中） | 直接对应成本 |
| 每轮工具数 / schema 大小 | 判断工具集是否臃肿 |
| 压缩次数与压缩后保留量 | 长对话的健康度 |
| 每轮丢弃段（budget 截断） | 判断预算是否太紧 |
| 每轮产出/成本比 | 判断 loop 是否在做无用功 |

## 9. 对 roostbot 的直接影响

1. **`packages/context`**：定义 Context Manifest（见同目录包），作为每轮可观测的产物。
2. **能力清单先于工具实现**：先定义“谁能用什么工具”，再决定 schema 怎么进上下文（未授权不可见）。
3. **记忆接口按“注入预算”设计**：causal-memory 的查询要支持 `budgetTokens` 与 `audience`，返回的不是一堆文本，而是排好序、带引用的段。
4. **技能按 token 计量**：一个技能的价值 = 它带来的行为改善 / 它占的上下文。
5. **调度与工作区**（另两份文档）只负责“启动 loop”和“保存 loop 之外的状态”，不掺上下文装配。

## 10. 待决问题

1. **上下文装配放在哪一层**：home runtime 内（DSH 插件）还是控制面？——倾向 runtime 内，控制面不碰 token。
2. **manifest 是否随回合持久化**：存卷（可回溯）还是只上报指标（省空间）？
3. **技能正文按需加载的触发**：模型主动读取（多一次往返），还是装配时按名字猜（零往返但可能多注入）？

## 11. manifest → 上下文：字段到分段的映射

`bot-manifest`（`request`）是声明，`ContextManifest`（`packages/context`）是每轮实际发生了什么。两者必须能对上，否则"声明了但没注入"这类问题无法发现。

| manifest 字段 | 变成哪个分段 | 何时 | 说明 |
|---|---|---|---|
| `instructions`（人设） | `persona` | 每轮常驻 | 稳定段，进缓存 |
| `description` / `role` | `system`（摘要一行） | 每轮常驻 | 让模型知道自己在团队里的位置 |
| `skills[]` | `skills-index`（常驻）+ `skill-body`（按需） | 索引常驻；正文按触发 | 索引只放名字 + 一句话 |
| `tools.allow` / `tools.deny` | `tool-schema` | 每轮 | **未列出 = 不进窗口**（deny-invisible） |
| `tools` 的执行结果 | `tool-result` | 调用后 | 超过阈值写附件，只留摘要 + 引用 |
| `memory.enabled/scopes` | `memory` | 回合开始 | 受 `budget.md` 的注入上限约束 |
| `model.tier` / `providerRef` | 不影响分段，影响**模型与成本** | — | 记录在 `turn.started` |
| `approvals[]` | 不进窗口 | 触发时 | 是门，不是上下文 |
| `schedule.checks` | 不进窗口 | 决定是否起 run | 纯代码，成本 0 |

**三条校验规则**（可写成测试）：

1. `tools.allow` 里每个工具，如果本轮没进 `tool-schema`，`ContextManifest` 必须记一条 `dropped(reason='cap'|'budget')`
2. `skills[]` 的名字必须在 `skills-index` 里出现一次（哪怕正文没注入）
3. `instructions` 为空时，`persona` 段必须存在且标注 `fallback`（防止"以为有人设"）

**为什么写这一节**：`loop-and-context.md` 说"技能是打包的上下文、工具是 schema + 结果"，`bot-manifest` 是这些打包的声明；两者之间缺一张映射表，就会在实现时各自解释。
